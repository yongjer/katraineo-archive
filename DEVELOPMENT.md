# Developing Katraineo

Katraineo is a [Tauri v2](https://v2.tauri.app/) desktop app: a React + TypeScript frontend with all of the go logic,
and a small Rust backend that runs KataGo. It started as a port of the original Python + Kivy KaTrain
([sanderland/katrain](https://github.com/sanderland/katrain)); the core logic was ported module by module and is tested
against data generated by the Python code, so the two behave the same and read and write the same SGF files.

## Layout

```
src/core/        Game logic with no UI or Tauri dependencies
  move.ts          moves and coordinates
  sgf.ts           SGF / NGF / GIB parsing, SGF writing
  gameNode.ts      game tree node + analysis bookkeeping (candidate moves, point loss, KT analysis cache)
  game.ts          board state and capture rules, navigation, analysis requests, extra analysis modes,
                   insert mode, self-play, region of interest
  engine.ts        KataGo analysis-engine client: query ids, priorities, pondering, result dispatch,
                   reconnecting to a remote engine
  ai.ts            AI strategies and rank estimation
  report.ts        player performance report
  tsumego.ts       tsumego frame
  models.ts        downloadable KataGo models
  i18n.ts          gettext lookup + Python-style format strings
src/state/       zustand store with the controller logic (AI turns, teaching, timer, pondering, files),
                 the user config (defaults.json holds the defaults) and the platform layer (Tauri or browser)
src/ui/          React components (SVG board, move tree, graph, panels, dialogs)
src/i18n/        translations (gettext .po files, one per language)
src/assets/      sounds
src-tauri/       Rust backend: runs KataGo (local process, custom command, or a WebSocket to a remote engine)
                 and streams its output as events; reads/writes files with encoding detection; stores the
                 config; downloads models
resources/       bundled KataGo binaries (Windows, Linux; macOS is built by scripts/build-katago-macos.sh),
                 the default model and the KataGo config
tests-ts/        unit tests (vitest), golden data generated from the Python implementation, test games
```

The Rust side deliberately knows nothing about go: it only owns the engine connection. KataGo's analysis engine
speaks JSON lines over stdin/stdout (or over a WebSocket for a remote engine), so the TypeScript `KataGoEngine`
talks to it through a small `EngineTransport` interface. The desktop app uses the Tauri transport; the tests use a
`child_process` transport, and `scripts/engine-bridge.mjs` provides one for working on the UI in a normal browser.

Paths in the config such as `katrain/models/...` refer to the bundled resources, as in the Python version, so
existing configs keep working.

## Commands

Prerequisites: Node 20+, Rust (stable), and the [Tauri system dependencies](https://v2.tauri.app/start/prerequisites/)
(on Debian/Ubuntu: `libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev libxdo-dev libssl-dev`).

```sh
npm install
npm run tauri dev        # desktop app with hot reload
npm run tauri build      # installers in src-tauri/target/release/bundle
npm test                 # unit tests
npm run typecheck
cargo test --manifest-path src-tauri/Cargo.toml
```

KataGo is bundled for Windows and Linux (`resources/KataGo`). For macOS, `scripts/build-katago-macos.sh` builds it
from source (Metal on Apple Silicon, OpenCL on Intel) with its Homebrew libraries copied next to it, as CI does;
run it once before `npm run tauri build` or `npm run tauri dev` on a Mac. Without a bundled KataGo the app falls
back to one on `PATH` or in Homebrew's folders (`brew install katago`).

On Linux the bundled `resources/KataGo/katago` is KataGo's own AppImage, so it needs FUSE (`libfuse2`). The packages
install it in `usr/share/Katraineo` rather than with the other resources in `usr/lib/Katraineo`, because linuxdeploy (used
to build Katraineo's AppImage) rewrites every ELF file below `usr/lib`, which corrupts it: it then crashes on start.
Programs started from inside Katraineo's AppImage must also not inherit the environment it sets up for itself
(`src-tauri/src/appimage.rs`).

The AppImage bundles the GStreamer plugins of the build machine (`bundleMediaFramework`), so building it needs
`gstreamer1.0-plugins-base gstreamer1.0-plugins-good gstreamer1.0-alsa gstreamer1.0-pulseaudio`. Without them, the web
view crashes the first time the app plays a sound.

The desktop entry on Linux finds the program (`katraineo`) on `PATH`. Do not use an absolute path in a desktop template: the AppImage uses the same entry, and would then
start the installed program instead of its own.

WebKitGTK's `<audio>` cannot load the app's own URLs, so `src/ui/sounds.ts` falls back to Web Audio there, with a new
`AudioContext` for each sound. To test it, count the sounds at the output with `parec` on the sink's `.monitor` while
two AIs play, and include a Bluetooth output: with one shared context, it only plays the first sound.

UI work in a browser (no Tauri), with a real engine:

```sh
npm run dev
node scripts/engine-bridge.mjs     # runs KataGo on 127.0.0.1:8765 and prints the URL to open (with a token)
```

End-to-end tests drive the real bundled KataGo from the TypeScript core:

```sh
KATAGO_E2E=1 npx vitest run tests-ts/engine.e2e.test.ts tests-ts/selfplay.e2e.test.ts
# include the human-like AIs:
KATAGO_E2E=1 KATAGO_HUMAN_MODEL=/path/to/b18c384nbt-humanv0.bin.gz npx vitest run tests-ts/engine.e2e.test.ts
```

Downloaded models are stored in the app data folder (`models/`); on macOS that is
`~/Library/Application Support/io.github.yongjer.katraineo/models`. Models in the Python version's `~/.katrain`
folder are offered as well.

### End-to-end tests of the app

`e2e/smoke.mjs` uses the installed app through WebDriver: it waits for KataGo, plays a move and waits for the AI's
answer, pastes a game and goes to a move, opens the settings and the report, and finds a test update (served over
https from a test certificate) whose bad signature it must refuse. `e2e/webdriver.mjs` is a small WebDriver client on
Node's `fetch`, so it needs no packages.

CI runs it on the Windows and Linux installers of every build (the `e2e` job), with KataGo's CPU build since the
runners have no GPU, and keeps screenshots, the KataGo log and the driver's output as the `e2e-*` artifacts. macOS is
not covered: there is no WebDriver for apps on WKWebView.

On Linux, [tauri-driver](https://v2.tauri.app/develop/tests/webdriver/) starts the app through WebKitWebDriver. On
Windows the test starts the app itself and attaches msedgedriver to it: msedgedriver can no longer start a WebView2 app
(WebView2 133 and later never open the debugging port it asks for). For that, a WebView2 policy gives the app a
debugging port, which CI sets under `AdditionalBrowserArguments` (value `katraineo.exe`,
`--remote-debugging-port=9222`), and the test gets the port in `E2E_WEBVIEW2_PORT`. Leave that policy off on your own
computer: any program on it can control the app through that port.

To run it on Linux: `cargo install tauri-driver --locked`, install WebKitWebDriver (`webkit2gtk-driver`, or
`webkitgtk-webdriver` on Ubuntu 26.04), build the app, and run it with a fresh config folder:

```sh
XDG_CONFIG_HOME=$(mktemp -d) KATRAINEO_APP=src-tauri/target/release/katraineo KATAGO=resources/KataGo/katago node e2e/smoke.mjs
```

## Translations

Translations are the gettext files in `src/i18n`. To improve one, edit the `msgstr` entries of that language's file.
To add a language, copy `en.po`, translate the `msgstr` entries (leave anything between `{}` as it is), and add the
language to `LANGUAGES` in `src/ui/i18nLoader.ts`.

## Disk writes reported by macOS

macOS can file a "disk writes" report for `katago-osx` in `/Library/Logs/DiagnosticReports`, for over 2 GB of "file backed
memory dirtied". That comes from Apple's MPSGraph compiling the model for Metal into temporary `payload-*.bin` files, and
it is not what reaches the disk: measured with `proc_pid_rusage`, a few GB of logical writes came with 0-32 MB of real ones.
The files do not stay behind.

## Test builds

Every push to `main` builds Windows, macOS (Apple Silicon and Intel) and Linux installers in CI and refreshes the
[`tauri-nightly` prerelease](https://github.com/yongjer/katraineo/releases/tag/tauri-nightly) with them.
These are unsigned test builds.

GitHub's macOS runners are often short of capacity, and it cancels a job that no runner picks up. When that happens to a
macOS build, `.github/workflows/retry-macos.yml` re-runs the failed jobs, up to three times. Other failures are left alone.

## Releases

The version is recorded in `package.json` (which `tauri.conf.json` reads), `package-lock.json`, `src-tauri/Cargo.toml`
and `Cargo.lock`. Windows Installer takes only numbers, so the MSI gets the version without its pre-release part
(`bundle > windows > wix > version`); an MSI replaces any installed version, so pre-releases still update.
`node scripts/set-version.mjs 2.0.0-alpha.2` sets them all, and `tests-ts/version.test.ts` checks that they agree. Linux gets
a `.deb` and an AppImage but no `.rpm`, whose version cannot have a pre-release part.

To release:

1. `node scripts/set-version.mjs <version>`, and merge that to `main`.
2. `git tag v<version>` on that commit and `git push origin v<version>`.
3. CI builds the installers, signs them for the updater, writes `latest.json`, and creates a **draft** release with all
   of them. Check it and publish it, **not as a pre-release**: the app reads
   `releases/latest/download/latest.json`, and GitHub's "latest" release is never a pre-release.

### Updates

The app checks for a newer version when it starts (unless *Check for updates at startup* is turned off in the general
settings) and from the menu, with tauri-plugin-updater (`src-tauri/src/updates.rs`). It installs the kind of package
it was installed from: the NSIS installer or the MSI on Windows (in passive mode; it closes the app, KataGo
included, and starts the new version), the app bundle on macOS, and the AppImage, or the `.deb` with `dpkg -i` after
asking for an administrator password, on Linux. `scripts/updater-manifest.mjs` writes `latest.json` with a
`<os>-<arch>-<package>` entry for each.

Updates are signed with a key from `tauri signer generate`. The public key is in `tauri.conf.json`
(`plugins > updater > pubkey`); the private key and its password are the repository secrets `TAURI_SIGNING_PRIVATE_KEY`
and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, which only the `release` job of the workflow reads. Without the private key
no installed copy can be updated again, so keep a copy of it somewhere safe. The signatures carry the version they were
made for, and the app requires it to match (`requireSignedVersion`), so an older release cannot be offered as a newer
one.

To try it without releasing anything:

* Run the workflow by hand with `release_preview` (Actions → Tauri app → Run workflow): it builds and signs the
  installers as for a release, and keeps the signatures and `latest.json` as an artifact.
* `KATRAINEO_UPDATE_ENDPOINT=https://.../latest.json` makes the app check that manifest instead of the latest release.
  It must be served over https.

## Not ported from the Python version

- Downloading KataGo binaries from the settings (set the path to a KataGo you downloaded instead)
- Contributing to KataGo's distributed training
- Themes and configurable keyboard shortcuts
- The minimalistic UI modes (`~` / `F12`)
